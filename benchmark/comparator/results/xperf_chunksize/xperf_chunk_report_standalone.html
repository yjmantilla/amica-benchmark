Fit time, convergence, and peak memory across AMICA implementations

We measured how long each Python AMICA implementation runs, how far it converges, and how much memory it needs on a real EEG dataset — sweeping each one across its batch/chunk-size setting on GPU and CPU. That single setting changes fit time by up to ~25× within one implementation; it also changes memory (for the torch implementations), and the fastest setting flips between GPU and CPU. The fit times are wall time to a fixed iteration budget, not time to an equivalent solution — read them with the convergence box below.

How to read this

The GPU fits are iteration-matched: every implementation's early-stops were disabled, so all run the full 3000 iterations. That removes the earlier confound of implementations quitting at different points — GPU wall time is now directly comparable per iteration (seconds/iteration × 3000 = wall time, exactly), so time differences reflect genuine per-iteration throughput, not who stopped early. At the largest chunk all four run 3,000/3,000 iterations. Three of the four land within ~0.001 nats of each other in final log-likelihood (jamica −1.1005, amica-python −1.1002, pyamica −1.0995); pAMICA is ~0.011 nats lower (−1.1107) in median — consistently, at matched iterations — i.e. a small but real convergence-quality gap, not an early-stop artifact (it runs the same 3000 iterations as the others and still lands ~0.011 nats lower; the measured iteration ladder below shows it still slowly improving at 3000 but far short of the others, and we did not test a larger budget). We do not verify that the four decompositions are numerically equivalent (component matching against the Fortran reference is not part of this pass); equal iterations is not proof of equal solutions. The CPU section further down is the earlier, non-iteration-matched run (its own caveats apply; a contention-free, iteration-matched CPU re-run is in progress — see that section).
~25×
Widest fit-time range across the setting within a single implementation (amica-python, GPU, iteration-matched). The others span 8–16×; every implementation is chunk-sensitive on time.

Peak VRAM grows with chunk for the torch impls (~2.7–3.6× NVML). jamica's GPU memory is flat in the median (~5.4 GiB; per-subject up to ~7.4 at 262K) on its chunked path — mostly a floor, not a dial.

On "the largest tested chunk." The biggest setting we swept is 262,144 samples. Each recording is 785,328–1,364,633 samples, so 262,144 is only ~19–33% of the data — it is the largest chunk tested, not a single full-batch pass. We label that axis point 262K, not "full-batch." True single-pass full-batch is a separate thing, discussed only for jamica in the memory note.

  • Larger chunks are faster on the GPU — for all four. Median fit time falls steeply as the chunk grows (jamica 775 s → 61 s; amica-python 5646 s → 230 s from 1024 to 262K, all at matched 3000 iterations). Small chunks under-utilise the device (utilisation not directly measured).
  • Memory grows with chunk for the torch implementations (amica-python ~1.8→4.9, pAMICA ~1.8→6.5, pyamica ~3.0→10.9 GiB NVML median). jamica's GPU memory is flat in the median (~5.4 GiB) across chunk on its chunked path — a chunk-independent full-width array sets the floor — though at 262K the longest recordings do rise (per-subject 5.4→7.4 GiB), so it is mostly, not entirely, a memory-flat dial. Nothing exceeded the 80 GiB card; the heaviest cell median is pyamica ~10.9 GiB (per-subject up to ~11.4).
  • The bands are tight now. With early-stops disabled every subject runs the same 3000 iterations, so the p25–p75 fit-time spread reflects only per-subject recording length (e.g. pAMICA at 262K is 258–267 s) — the wide, early-stop-driven scatter of the previous run is gone.

Convergence vs iterations — the measured iteration ladder

A direct, measured convergence view (not a post-hoc estimate): at a fixed chunk (65536) with early-stops disabled, we ran every implementation to 100, 250, 500, 1000, 2000 and 3000 iterations and recorded the median final log-likelihood at each — all 25 subjects at every point. This shows how fast each implementation's solution quality improves with iterations, orthogonal to the per-iteration wall-time above.

pAMICA-1.1293-1.1202-1.1179-1.1151-1.1122-1.1107320s
  • jamica converges fastest in both iterations and wall time. It is within ~0.001 nats of its own final LL by ~500 iterations (−1.1013 at 500 → −1.1005 at 3000), and because it is ~4–5× cheaper per iteration it gets there in ~14 s — versus ~51–57 s for the others to run the same 500 iterations.
  • pyamica reaches the best (least-negative) reported LL (−1.0995) but uses most of the budget to squeeze the last fraction; amica-python tracks it and plateaus around −1.1006.
  • pAMICA stays ~0.011 nats lower across the whole ladder. Its LL climbs from −1.1293 (100) to −1.1107 (3000) but never reaches the other three's ~−1.100. It is still improving at the end (~0.0016 nats over the last 1000 iters, vs ≤0.0001 for the others), so this is a genuine convergence-quality gap at matched iterations — not an early-stop artifact. We did not run past 3000, so the honest claim is that the gap persists through 3000 and is not closing at any practical budget, not that it can never close.

The exact per-cell winner is not resolved and we do not name a per-impl optimum: the by-subject bands are wide (contention) and coverage is unequal (a cell missing the longest recording looks artificially fast — e.g. jamica's 4K cell drops one subject), so read only the broad small/mid-vs-large flip.

  • One setting failed: pyamica at 1024 (hundreds–thousands of eager blocks/iter) exceeded the 12 h wall — absent from the curve.
On the CPU numbers. Three confounds, all disclosed here: (1) contention — CPU fits ran on shared cluster nodes, AMICA is memory-bandwidth-bound, and the cluster was busy throughout (no quiet window), which is why the p25–p75 bands are wide; (2) unequal subject coverage — cells contain 1–5 subjects (see the *n marks), so a cell missing the longest recording looks artificially fast. We therefore aggregate by subject (median within subject, then across subjects) and still treat absolute CPU seconds and exact per-cell optima as unresolved — only the broad device flip is trustworthy. CPU memory scales with chunk (and with recording length). Fortran is single-threaded (OMP_NUM_THREADS=1); per core-second it is actually more efficient than the 8-thread Python impls, so it is a reference footprint, not a head-to-head. And (3) these CPU fits are not iteration-matched — unlike the GPU section above, they used each implementation's own early-stop under a 1000-iteration cap, so CPU wall times are not directly per-iteration-comparable and are read only for the coarse device flip. Detail + per-cell data: NOTES_measurement.md, raw/.

A note on the memory numbers

NVML is the framework-neutral VRAM figure. The per-framework allocator counters (JAX peak_bytes_in_use, torch max_memory_allocated) measure only live-tensor bytes in each framework's own allocator — they omit the CUDA/cuDNN context and the pool the driver actually holds, and the two frameworks count differently, so they are not comparable across implementations and understate the real footprint by ~1.2–3.3× across the 25 measured impl×chunk pairs (all in raw/chunk_gpumem_summary.csv) — e.g. jamica chunked ~1.6 GiB allocator vs ~5.3 GiB NVML ≈ 3.3× at small chunks, shrinking to pyamica@262K ~1.2× at the largest chunk (the gap shrinks as live tensors grow to dominate the fixed context + pool overhead). The charts use NVML whole-GPU 'used' on a dedicated GPU. Two caveats on that meter: it is a 50 ms poll (a sub-interval spike could be missed), and the frameworks run under different allocator settings (JAX with pre-allocation off; torch with its caching allocator on), so NVML is a neutral meter over somewhat different protocols.

Measured medians (GiB) across 25 subjects: context = whole-GPU used right after the CUDA context is forced, before model/data; live-alloc = framework allocator live-tensor peak; NVML total = whole-GPU peak. This pre-fit baseline is ~1 GiB for all four (JAX 1.02, torch 1.08) — essentially equal. It is measured before the fit, so any kernel/cuDNN state loaded lazily during fitting falls into the remainder below, not this baseline; we therefore claim only that the measured pre-fit floor does not differ across frameworks, not that the complete fixed framework context is ~1 GiB. What differs is the resident/pool memory: torch's NVML ≈ baseline + its live/reserved pool (and scales with chunk), whereas jamica's allocator peak stays small (~1.9) while its NVML is ~5.4 — JAX holds a larger, chunk-independent resident/pool footprint the allocator counter undercounts most.

jamica memory is two-level, and it cuts both ways. On its chunked path jamica's median NVML is ~5.4 GiB across chunk sizes (per-subject ~3.4–5.4 GiB below 262K, rising to 5.4–7.4 GiB at 262K for the longest recordings — flat in the median across chunk, a floor, not a single constant). Its full-batch path (chunk_size=None — a different orchestrator key, and jamica's shipped default) uses ~13.4 GiB NVML median (per-subject up to ~21 for the longest recording) for essentially the same GPU speed (~0.020 vs ~0.020 s/iter — no chunk benefit on GPU; the full-batch figure is from the earlier memory run). On CPU, chunking helps both axes (~1,985 s / ~2.2 GiB chunked vs ~4,300 s / ~20 GiB full-batch). So under these tested conditions a wrapper should pass a chunk. The flip side, in fairness: jamica's ~5.4 GiB chunked floor is higher than the torch impls' small-chunk footprint (~1.8–3.1 GiB NVML) — on a small card the torch impls at a small chunk fit where jamica may not. (The "fits an 8–12 GiB card" reading is an extrapolation from H100 NVML with JAX pre-allocation off; it was not measured on such a card.)

"Flat jamica memory" is not the earlier full-batch measurement bug. Flat memory was the signature of a fixed bug where jamica was accidentally run full-batch at every chunk, so we checked. Two things rule it out here: (1) jamica's fit time varies ~13× with the chunk (775 s→61 s) — only possible if the chunk is actually applied; the true full-batch path is chunk-independent in time too (~61 s at every chunk). (2) The chunked path's memory (~5.4 GiB NVML / ~1.9 GiB allocator) is less than half the full-batch path's (~13.4 / 8.2 GiB) — different numbers, different code path (both in raw/chunk_gpumem_summary.csv). The chunked NVML is flat because of what it's made of: the measured context floor is only ~1 GiB (chunk-independent, and about the same for JAX and torch — see the decomposition above), and the rest of the ~5.4 GiB is JAX's memory pool plus chunk-independent resident arrays (the whitened data and source outputs, sized by n_samples); the framework allocator counter (peak_bytes_in_use ~1.9 GiB) undercounts that resident/pooled footprint the most for JAX, which is why jamica's NVML sits far above its allocator peak. The chunk-scaled E-step block buffer is small next to the resident arrays until 262K, where it begins to add (allocator 1.6→1.9 GiB; per-subject NVML up to ~7.4). So chunk is a real time dial for jamica but not a GPU-memory dial — a genuine property of the chunked path, distinct from the full-batch key. And it is by design, not a leak: the chunked E-step accumulates small per-chunk sufficient statistics (O(n_comp²)) and never materialises the full-width (n_comp, n_samples) per-sample tensors — those appear only on the full-batch path. Of the ~5.4 GiB whole-GPU NVML, only ~1 GiB is the measured pre-fit context floor and ~1.6 GiB is the allocator's live-tensor peak (resident whitened data + accumulators); the remaining ~2.4 GiB is JAX pool / resident bytes the allocator counter does not report / post-init runtime, which we do not separate further — it is chunk-independent (see the decomposition above). Chunking bounds the chunk-scaled working set as intended; it simply cannot go below that context + pool + resident-data floor (which is not a ~3.8 GiB context — the context alone is ~1 GiB).
