Fit time, convergence, and peak memory across AMICA implementations

We measured how long each Python AMICA implementation runs, how far it converges, and how much memory it needs on a real EEG dataset — sweeping each one across its batch/chunk-size setting on GPU and CPU. That single setting changes fit time by up to ~25× within one implementation; it also changes memory (for the torch implementations), and the fastest setting flips between GPU and CPU. The fit times are wall time to a fixed iteration budget, not time to an equivalent solution — read them with the convergence box below.

How to read this

These are wall times to a fixed iteration budget — not a convergence race. Every fit was capped at 3000 iterations on GPU / 1000 on CPU. But the implementations do not all use that budget the same way. At the largest chunk on GPU, the actual iterations run before each one stopped were: pyamica 3000 (always runs the full cap), jamica 2,444–3,000, scott-huberty 784–1,654 (early-converges and stops well before the cap), pAMICA 151–3,000 (its early-stop can fire very early). They reach final log-likelihoods in a tight but non-identical band (about −1.10 to −1.12; pAMICA's is the lowest). So a shorter wall time can mean a faster implementation, an earlier stop, or fewer iterations of work — not necessarily a better or equally-finished decomposition. Equal budget is not equal work, and not equal convergence. We report n_iter and ll_final alongside time so you can see which is which. We also do not verify that the four decompositions are numerically equivalent (component matching against the Fortran reference is not part of this pass).

On "the largest tested chunk." The biggest setting we swept is 262,144 samples. Each recording is 785,328–1,364,633 samples, so 262,144 is only ~15–33% of the data — it is the largest chunk tested, not a single full-batch pass. We label that axis point 262K, not "full-batch." True single-pass full-batch is a separate thing, discussed only for jamica in the memory note.

  • Larger chunks are faster on the GPU — for all four. Median fit time falls steeply as the chunk grows (jamica 763 s → 62 s; scott-huberty 2024 s → 79 s from 1024 to 262K). Small chunks starve the device.
  • Memory grows with chunk for the torch implementations (scott-huberty ~1.8→4.9, pAMICA ~1.8→6.6, pyamica ~3.0→10.9 GiB NVML). jamica's GPU memory is flat at ~5.4 GiB on its chunked path — a chunk-independent full-width array sets a floor, so for jamica the chunk is a time dial but not a GPU-memory dial. Nothing exceeded the 80 GiB card at this budget (peak ~10.9 GiB).
  • The bands are informative. pAMICA's wide 262K band reflects its early-stop firing at very different iteration counts across subjects (see the convergence box).

  • The fastest setting flips on CPU. CPU is fastest at small/mid chunks (jamica 1024, scott-huberty ~4096) — the opposite of the GPU, where large chunks won. Small blocks fit CPU cache. But the CPU bands are wide (contended cluster): several apparent optima sit inside the noise — scott-huberty 4096 vs 16384 differ <1%, jamica 1024 vs 4096 ~5%. Trust the broad small-chunk tendency, not the exact per-impl optimum.
  • CPU AMICA is a heavy method (tens of minutes to hours at 1000 iterations): jamica ~1980 s at its best CPU setting, scott-huberty ~2790 s, pAMICA ~3580 s, then pyamica and Fortran in the thousands of seconds. Compare absolute CPU seconds only coarsely.
  • Memory grows with chunk on CPU too (pyamica ~9.8, jamica ~7 GiB at 262K); small chunks bring everyone to ~1.6–2.2 GiB. The single-threaded Fortran reference is leanest everywhere (0.6→3.1 GiB).
  • One setting failed: pyamica at 1024 (hundreds–thousands of eager blocks/iter) exceeded the 12 h wall — absent from the curve.
On the CPU timing numbers. CPU fits ran on shared cluster nodes; AMICA is memory-bandwidth-bound, so co-located jobs interfere. The cluster was busy throughout (repeated cells found no quiet window), which is why the p25–p75 bands are wide and some cells are non-monotonic. We report the median over 5 subjects × reps; treat absolute CPU seconds as contention-inflated and rely on the broad shapes and the device flip, not exact seconds or fine ordering. CPU memory is allocation-driven and clean. Fortran is single-threaded (OMP_NUM_THREADS=1); per core-second it is actually more efficient than the 8-thread Python impls, so keep it as a reference footprint, not a head-to-head. Detail: NOTES_measurement.md.

A note on the memory numbers

NVML is the framework-neutral VRAM figure. The per-framework allocator counters (JAX peak_bytes_in_use, torch max_memory_allocated) measure only live-tensor bytes in each framework's own allocator — they omit the CUDA/cuDNN context and the pool the driver actually holds, and the two frameworks count differently, so they are not comparable across implementations and understate the real footprint (by ~1.4–3.4× in the pairs we can check; e.g. jamica chunked ~1.6 GiB allocator vs ~5.4 GiB NVML = 3.4×; jamica full-batch 8.2 vs 11.4 GiB = 1.4×). The charts use NVML whole-GPU 'used' on a dedicated GPU. Two caveats on that meter: it is a 50 ms poll (a sub-interval spike could be missed), and the frameworks run under different allocator settings (JAX with pre-allocation off; torch with its caching allocator on), so NVML is a neutral meter over somewhat different protocols.

jamica memory is two-level, and it cuts both ways. On its chunked path jamica sits at ~5.4 GiB NVML across chunk sizes. Its full-batch path (chunk_size=None — a different orchestrator key, and jamica's shipped default) uses ~11 GiB NVML for essentially the same GPU wall time (~61 s vs ~62 s at 3000 iters — measured, no speed benefit). On CPU, chunking helps both axes (~1,982 s / ~2.2 GiB chunked vs ~4,000 s / ~20 GiB full-batch). So a wrapper should always pass a chunk. The flip side, in fairness: jamica's ~5.4 GiB chunked floor is higher than the torch impls' small-chunk footprint (~1.8–3.1 GiB NVML) — on a small card the torch impls at a small chunk fit where jamica may not. (The "fits an 8–12 GiB card" reading is an extrapolation from H100 NVML with JAX pre-allocation off; it was not measured on such a card.)
