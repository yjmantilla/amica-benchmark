Fit time, convergence, and peak memory across AMICA implementations

We measured how long each Python AMICA implementation runs, how far it converges, and how much memory it needs on a real EEG dataset — sweeping each one across its batch/chunk-size setting on GPU and CPU. That single setting changes fit time by up to ~25× within one implementation; it also changes memory (for the torch implementations), and the fastest setting flips between GPU and CPU. The fit times are wall time to a fixed iteration budget, not time to an equivalent solution — read them with the convergence box below.

How to read this

These are wall times to a fixed iteration budget — not a convergence race. Every fit was capped at 3000 iterations on GPU / 1000 on CPU, but the implementations do not use that budget the same way, because each stops on its own early-stop default (Fortran's is disabled; the others differ). At the largest chunk on GPU the median iterations actually run were: pyamica 3,000 (always runs the full cap), jamica 3,000 (range 2,572–3,000), pAMICA 3,000 (but its early-stop can fire as low as 151), scott-huberty 1,106 (786–1,654 — it converges and stops well before the cap). Three of the four land within ~0.002 nats of each other in final log-likelihood (jamica −1.1016, scott −1.1004, pyamica −1.0995); pAMICA is ~0.02 nats lower (−1.1204) in median — and a paired per-subject delta of ~0.007 nats, negative for every subject — i.e. a small but consistent, meaningfully worse fit at this budget, not merely "the lowest." So a shorter wall time can mean a faster implementation, an earlier stop, or fewer iterations of work. To normalize per-iteration cost, the GPU table below also reports seconds/iteration (median of per-subject time÷iterations-run). We do not verify that the four decompositions are numerically equivalent (component matching against the Fortran reference is not part of this pass); equal budget is not equal work, and not equal convergence.

On "the largest tested chunk." The biggest setting we swept is 262,144 samples. Each recording is 785,328–1,364,633 samples, so 262,144 is only ~19–33% of the data — it is the largest chunk tested, not a single full-batch pass. We label that axis point 262K, not "full-batch." True single-pass full-batch is a separate thing, discussed only for jamica in the memory note.

  • Larger chunks are faster on the GPU — for all four. Median fit time falls steeply as the chunk grows (jamica 763 s → 62 s; scott-huberty 2024 s → 79 s from 1024 to 262K). Small chunks starve the device.
  • Memory grows with chunk for the torch implementations (scott-huberty ~1.8→4.9, pAMICA ~1.8→6.6, pyamica ~3.0→10.9 GiB NVML median). jamica's GPU memory is flat in the median (~5.4 GiB) across chunk on its chunked path — a chunk-independent full-width array sets the floor — though at 262K the longest recordings do rise (per-subject 5.4→7.4 GiB), so it is mostly, not entirely, a memory-flat dial. Nothing exceeded the 80 GiB card; the heaviest cell median is pyamica ~10.9 GiB (per-subject up to ~11.4).
  • The bands are informative. pAMICA's wide 262K band reflects its early-stop firing at very different iteration counts across subjects (see the convergence box).

  • The fastest setting flips on CPU. The Python implementations are fastest at small/mid chunks (roughly 1K–16K) — the opposite of the GPU, where large chunks won — consistent with a cache effect (small blocks stay resident; not directly measured). The exact per-cell winner is not resolved and we do not name a per-impl optimum: the by-subject bands are wide (contention) and coverage is unequal (a cell missing the longest recording looks artificially fast — e.g. jamica's 4K cell drops one subject), so read only the broad small/mid-vs-large flip.
  • CPU AMICA is a heavy method (tens of minutes to hours at 1000 iterations): jamica ~2000 s at its best CPU setting, scott-huberty ~2600 s, pAMICA ~3900 s, pyamica ~10⁴ s. Compare absolute CPU seconds only coarsely.
  • Memory grows with chunk on CPU too (pyamica ~9.8, jamica ~7 GiB at 262K); small chunks bring the Python impls to ~1.6–2.2 GiB. The single-threaded Fortran reference is leanest in absolute terms (0.6→3.1 GiB), though those cells are largely single-subject.
  • One setting failed: pyamica at 1024 (hundreds–thousands of eager blocks/iter) exceeded the 12 h wall — absent from the curve.
On the CPU numbers. Two confounds, both disclosed here: (1) contention — CPU fits ran on shared cluster nodes, AMICA is memory-bandwidth-bound, and the cluster was busy throughout (no quiet window), which is why the p25–p75 bands are wide; (2) unequal subject coverage — cells contain 1–5 subjects (see the *n marks), so a cell missing the longest recording looks artificially fast. We therefore aggregate by subject (median within subject, then across subjects) and still treat absolute CPU seconds and exact per-cell optima as unresolved — only the broad device flip is trustworthy. CPU memory scales with chunk (and with recording length). Fortran is single-threaded (OMP_NUM_THREADS=1); per core-second it is actually more efficient than the 8-thread Python impls, so it is a reference footprint, not a head-to-head. Detail + per-cell data: NOTES_measurement.md, raw/.

A note on the memory numbers

NVML is the framework-neutral VRAM figure. The per-framework allocator counters (JAX peak_bytes_in_use, torch max_memory_allocated) measure only live-tensor bytes in each framework's own allocator — they omit the CUDA/cuDNN context and the pool the driver actually holds, and the two frameworks count differently, so they are not comparable across implementations and understate the real footprint by ~1.2–3.3× across the 25 measured impl×chunk pairs (all in raw/chunk_gpumem_summary.csv) — e.g. jamica chunked 1.94 GiB allocator vs 5.37 GiB NVML = 2.8× at the small end, pyamica@262K 1.2× at the large end (the gap shrinks as live tensors grow to dominate the fixed context). The charts use NVML whole-GPU 'used' on a dedicated GPU. Two caveats on that meter: it is a 50 ms poll (a sub-interval spike could be missed), and the frameworks run under different allocator settings (JAX with pre-allocation off; torch with its caching allocator on), so NVML is a neutral meter over somewhat different protocols.

jamica memory is two-level, and it cuts both ways. On its chunked path jamica's median NVML is ~5.4 GiB across chunk sizes (per-subject ~3.4–5.4 GiB below 262K, rising to 5.4–7.4 GiB at 262K for the longest recordings — flat in the median across chunk, a floor, not a single constant). Its full-batch path (chunk_size=None — a different orchestrator key, and jamica's shipped default) uses ~13.4 GiB NVML median (per-subject up to ~21 for the longest recording) for essentially the same GPU speed (~0.020 vs ~0.021 s/iter, same run — no chunk benefit on GPU). On CPU, chunking helps both axes (~1,985 s / ~2.2 GiB chunked vs ~4,300 s / ~20 GiB full-batch). So under these tested conditions a wrapper should pass a chunk. The flip side, in fairness: jamica's ~5.4 GiB chunked floor is higher than the torch impls' small-chunk footprint (~1.8–3.1 GiB NVML) — on a small card the torch impls at a small chunk fit where jamica may not. (The "fits an 8–12 GiB card" reading is an extrapolation from H100 NVML with JAX pre-allocation off; it was not measured on such a card.)
