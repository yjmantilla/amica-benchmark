Fit time and peak memory across AMICA implementations

We measured how long each Python AMICA implementation takes to fit, and how much memory it needs, on a real EEG dataset — sweeping each one across its batch/chunk-size setting on both GPU and CPU, at a realistic iteration budget. That single setting changes fit time by up to ~25× within one implementation and its peak memory by several-fold, and the best setting flips between GPU and CPU. All four implementations behave the same way here — it's a shared dial.

What we measured

Each implementation exposes a setting controlling how many samples are processed per pass — chunk_size, block_size, chunk_t or batch_size depending on the package. We swept it across five values (1024 → full-batch) and recorded fit time and peak memory on the same subjects, per device, at a realistic budget (GPU 3000 iterations, CPU 1000). jamica is measured on its chunked code path.

GPU — fit time & memory

Each implementation swept across its setting on real ds004505 (per-subject median, 3000 iterations, H100). ◯ marks each one's fastest measured setting. VRAM is the NVML whole-GPU peak — the framework-neutral figure (see the memory note below).

  • Larger settings are faster on the GPU — for all four. Fit time falls steeply as the chunk grows (e.g. jamica 763 s → 62 s, scott-huberty 2024 s → 79 s from 1024 to full-batch). The fastest setting is at or near full-batch for every implementation.
  • Small settings are slow. At 1024, fit times run 760 s (jamica) to 4090 s (pAMICA) versus 62–295 s at each one's own fastest setting — a per-implementation optimum only found by sweeping.
  • Chunking cuts peak memory. Full-batch is the heavy end (pyamica ~11 GB NVML, pAMICA ~6.6, jamica ~5.4, scott-huberty ~4.9); chunking down brings the torch impls to ~2–3 GB. Nothing ran out of memory on the 80 GB card at this budget.

CPU — fit time & memory

Real ds004505, 8 cores, 5 subjects, 1000 iterations. ◯ marks each implementation's fastest CPU setting. Includes the Fortran amica17 reference (CPU-only, single-threaded).

  • The best setting flips on CPU. CPU optima sit at small/mid chunks (jamica 1024, scott-huberty/pAMICA ~4096, pyamica 65536) — the opposite of the GPU, where full-batch won. Small blocks fit CPU cache; on the H100 they starve the device. The recommended setting depends on the device.
  • CPU is minutes, not seconds. At its best CPU setting jamica is ~1980 s (33 min) at 1000 iterations, scott-huberty ~2790 s, pAMICA ~3580 s, Fortran ~5300 s, pyamica the slowest (~9300 s at its optimum) — AMICA on CPU is a heavy, hours-scale method.
  • Memory scales with chunk on CPU too. Full-batch is heaviest (pyamica ~9.8 GB, jamica ~7 GB); small chunks bring everyone to ~1.6–2.2 GB. The Fortran reference is leanest everywhere (0.6 GB at 1024 → 3.1 GB full-batch).
  • One setting failed: pyamica at 1024 (~767 eager blocks/iter) exceeded the 12 h wall — absent from the curve.
On the CPU timing numbers. CPU fits ran on shared cluster nodes; AMICA is memory-bandwidth-bound, so co-located jobs interfere and per-cell absolute times are contention-inflated (the cluster was busy throughout — repeated cells found no quiet window). We report the median over 5 subjects × 5 repetitions; treat the absolute CPU seconds as approximate and rely on the curve shapes and each implementation's fastest setting. CPU memory is allocation-driven and clean. Fortran is single-threaded (OMP_NUM_THREADS=1), so its per-core cost is not comparable to the 8-thread Python impls. Detail: NOTES_measurement.md.

A note on the memory numbers

NVML is the honest VRAM figure. The per-framework allocator counters (JAX peak_bytes_in_use, torch max_memory_allocated) measure only live-tensor bytes in each framework's own allocator — they omit the CUDA/cuDNN context and pool the driver actually holds, and the two frameworks count differently, so they are not comparable across implementations and understate the real footprint by roughly 2×. The charts above use NVML whole-GPU 'used' on a dedicated GPU, which is framework-neutral and reflects what would actually fit on a card. (Example: jamica's allocator peak is ~1.6 GB but its NVML footprint is ~5.4 GB.)

jamica memory is two-level. On its chunked path jamica sits at ~5.4 GB NVML across chunk sizes (a chunk-independent full-width array dominates the peak). Its full-batch path (chunk_size=None) is a different code path that materialises the full-width arrays for ~11 GB NVML — at no speed benefit over chunked-at-full. So a wrapper should always pass a chunk, never leave jamica on the full-batch path. A ~5 GB chunked footprint fits the 8–12 GB cards many users have; the ~11 GB full-batch path may not.
