Cross-implementation AMICA · ds004505 · real EEG

Fit time, convergence, and peak memory across AMICA implementations

Every Python AMICA implementation exposes one batch/chunk-size knob. We swept it on real EEG (ds004505), GPU and CPU, at matched iterations — and it is a big dial. Three takeaways: on the GPU most of the speed-up is in by a ~262K chunk (a little more out to 1M, paid for in memory); GPU memory climbs steeply with the chunk (pyamica reaches ~30 GiB at full-batch — enough to matter on smaller cards); and for the four parallel implementations, small chunks are fastest on neither device. Fit times are wall time to a fixed iteration budget, not time to an equivalent solution — read them with the convergence section.

How to read this

The GPU fits are iteration-matched — early-stops disabled, so all four run the full 3000 iterations and GPU wall time is directly comparable per iteration (seconds/iteration × 3000 = wall, exactly). At matched iterations three of the four land within ~0.001 nats in final log-likelihood (jamica −1.1005, amica-python −1.1002, pyamica −1.0995); pAMICA sits ~0.011 nats lower (−1.1107) — a small but real convergence-quality gap (detailed in the iteration ladder), not just an effect of stopping at different points. Equal iterations is not proof of equal solutions — we did not check that the results are identical decompositions. The CPU section is a separate run on a 64-core machine at 250 iterations: clean absolute times, but a different iteration count from the GPU's — don't compare GPU and CPU seconds.

  • Larger chunks are faster on the GPU — but the win saturates by ~262K. Fit time falls steeply over the small chunks (jamica 775 s → 61 s; amica-python 5646 s → 230 s from 1024 to 262K), then is essentially flat from 262K on (across 262K→1M: jamica ~61→59 s, amica-python 230→209, pyamica 296→284, pAMICA 262→248 s; full-batch in the table below). So 262K already captures almost all of the GPU speedup; going bigger buys little time and costs a lot of memory.
  • Memory rises steeply with the chunk. Total GPU memory grows for every implementation (262K→1M: pyamica 10.9→28.1, pAMICA 6.5→19.3, amica-python 4.9→13.3, jamica 5.4→13.4 GiB; full-batch in the table). Everything fit the card used here (80 GiB), but the capacity lines put the numbers in context: pyamica's footprint passes 24 GiB by ~1M and reaches ~29.6 GiB at full-batch, so it would not fit a 24 GiB card if those numbers carry over to smaller hardware (not tested here). jamica stays flat (~5.4 GiB) only through 262K, then steps up to ~13.4 GiB at 512K and holds — so for jamica the chunk setting only starts to move memory once the chunk is large.
  • amica-python will not accept a chunk larger than the recording. A single oversized value fails for every subject, so its full-batch result uses a chunk equal to each recording's own length (14.1 GiB of GPU memory — comfortably within the card; this was a setting limit, not running out of memory). A note on the memory numbers

Three memory numbers — and why the smallest one can still crash a run. The charts report the memory actually used on the card ("total GPU memory"), measured independently of any framework. Each framework also reports how much it has actively in use, but that number understates the real footprint by about 1.2–3.3× at small-to-mid chunks (shrinking toward ~1× at the largest chunks, where the working set dominates) — it leaves out fixed start-up cost and the memory the software holds in reserve — and the frameworks count it differently, so it isn't comparable across implementations. The number that matters for running out of memory is the reserved memory (the pool the software holds), not the actively-used figure — which is why an implementation with a modest "in use" number can still be close to the limit. The three nest: in active use ≤ reserved ≤ total.

The four panels above (per-subject median, chunk axis through 1M; full-batch is in the table earlier): memory in active use (each framework's own count), memory reserved (what the software holds — the number that runs out first), total GPU memory used, and how much the "active" number understates the total (largest for jamica at small chunks, about 3×, shrinking as the working memory grows). All climb with the chunk for the three torch implementations; jamica stays flat until the chunk passes a mid size, then steps up.

jamica's memory comes in two levels. Through a 262K chunk it holds a flat floor of about 5 GiB, then steps up to about 13 GiB for large chunks and stays there. This is real, not a measurement quirk: jamica's fit time changes about 13× across the chunk range (roughly 775 s down to 61 s), which only happens if the chunk setting is genuinely being applied. The floor exists because jamica keeps small running summaries per chunk instead of holding the whole recording at once, so its working memory is bounded — about 1 GiB of fixed start-up cost plus a few GiB of resident data that do not depend on the chunk, until the chunk itself becomes large. It cuts both ways: jamica's ~5 GiB floor is higher than the others' ~2–3 GiB at small chunks (on a small card they may fit where jamica does not), but jamica never climbs the way pyamica does.

Each implementation at chunk 262K on the H100 (per-subject median), all run for the same 3000 iterations. Seconds per iteration folds in fixed start-up cost, and the implementations' update rules differ, so it is not a pure kernel-speed number. jamica has both the shortest wall time and by far the lowest cost per iteration (~0.020 s/iter vs 0.077–0.099 for the others — ~3.8–4.9× faster per iteration).   • jamica converges fastest in both iterations and wall time. It is within ~0.001 in log-likelihood (measured in nats, the natural-log units; 0.001 is a very small difference) of its own final LL by ~500 iterations (−1.1013 at 500 → −1.1005 at 3000), and because it is ~3.8–4.9× cheaper per iteration it gets there in ~14 s — versus ~51–57 s for the others to run the same 500 iterations.
  • pyamica reaches the best (least-negative) reported LL (−1.0995) but uses most of the budget to squeeze the last fraction; amica-python tracks it and plateaus around −1.1006.
  • pAMICA sits below the other three at every iteration count. Its log-likelihood climbs from −1.1293 (100) to −1.1107 (3000) but never reaches the other three's ~−1.100 — a gap that is wider early (~0.015 at 100 iterations) and narrows to ~0.011 by 3000. It is still improving at the end (~0.0016 over the last 1000 iterations, versus ≤0.0001 for the others), so the gap is genuine at the same iteration count — not an effect of stopping early — and is still narrowing at 3000; we did not measure beyond that, so whether it eventually closes is untested.

Bands overlap between adjacent chunks, so read these as lowest measured medians, not certified optima.
  • The smallest chunk is fastest for none of the four parallel implementations, and the best setting depends on the implementation. jamica and amica-python are fastest at the largest chunk; pAMICA and pyamica are fastest at a mid-size chunk (pyamica is ~10% slower at the largest and about 2× slower at a 64K chunk). So the curves are not a smooth "bigger is better". The single-threaded reference is roughly flat, marginally best at the smallest chunk.
  • AMICA is a heavy method on the CPU — even at 250 iterations it is ~13–25 min per fit for the four main implementations and about an hour for the single-threaded reference; at a full 3000-iteration run that is hours. A GPU is far preferable.
  • Memory grows with the chunk on the CPU too (jamica ~2.3→10.4, pyamica ~2.1→9.6, pAMICA ~1.6→6.1 GiB from the smallest to the largest chunk); the single-threaded reference is leanest (0.8→3.1 GiB). As on the GPU, memory does not depend on the number of iterations.
How to read the CPU numbers. Each fit had a whole machine to itself, so the absolute times are meaningful. The spread across subjects varies (from small to fairly wide depending on the setting), so differences of a few percent between neighbouring chunks are not reliable — trust the overall shape, not an exact best chunk. The four main implementations used all 64 cores; the reference implementation is single-threaded, so treat it as a footprint rather than a like-for-like speed comparison. The GPU and CPU runs use different iteration counts, so don't compare their seconds.
