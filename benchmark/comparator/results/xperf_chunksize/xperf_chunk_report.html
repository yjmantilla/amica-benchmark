Fit time, convergence, and peak memory across AMICA implementations

We measured how long each Python AMICA implementation runs, how far it converges, and how much memory it needs on a real EEG dataset — sweeping each one across its batch/chunk-size setting on GPU and CPU. That single setting changes fit time by up to ~25× within one implementation; it also changes memory (for the torch implementations), and the fastest setting is device- and implementation-specific (small chunks are best on neither device). The fit times are wall time to a fixed iteration budget, not time to an equivalent solution — read them with the convergence box below.

How to read this

The GPU fits are iteration-matched: every implementation's early-stops were disabled, so all run the full 3000 iterations. That removes the earlier confound of implementations quitting at different points — GPU wall time is now directly comparable per iteration (seconds/iteration × 3000 = wall time, exactly), so time differences reflect genuine per-iteration throughput, not who stopped early. At the largest chunk all four run 3,000/3,000 iterations. Three of the four land within ~0.001 nats of each other in final log-likelihood (jamica −1.1005, amica-python −1.1002, pyamica −1.0995); pAMICA is ~0.011 nats lower (−1.1107) in median — consistently, at matched iterations — i.e. a small but real convergence-quality gap, not an early-stop artifact (it runs the same 3000 iterations as the others and still lands ~0.011 nats lower; the measured iteration ladder below shows it still slowly improving at 3000 but far short of the others, and we did not test a larger budget). We do not verify that the four decompositions are numerically equivalent (component matching against the Fortran reference is not part of this pass); equal iterations is not proof of equal solutions. The CPU section further down is a separate whole-node, iteration-matched run (250 iters) — clean absolutes, but its iteration budget differs from the GPU's, so don't compare GPU and CPU seconds directly.

On "the largest tested chunk." The biggest setting we swept is 262,144 samples. Each recording is 785,328–1,364,633 samples, so 262,144 is only ~19–33% of the data — it is the largest chunk tested, not a single full-batch pass. We label that axis point 262K, not "full-batch." True single-pass full-batch is a separate thing, discussed only for jamica in the memory note.

A note on the memory numbers

NVML is the framework-neutral VRAM figure. The per-framework allocator counters (JAX peak_bytes_in_use, torch max_memory_allocated) measure only live-tensor bytes in each framework's own allocator — they omit the CUDA/cuDNN context and the pool the driver actually holds, and the two frameworks count differently, so they are not comparable across implementations and understate the real footprint by ~1.2–3.3× across the 25 measured impl×chunk pairs (all in raw/chunk_gpumem_summary.csv) — e.g. jamica chunked ~1.6 GiB allocator vs ~5.3 GiB NVML ≈ 3.3× at small chunks, shrinking to pyamica@262K ~1.2× at the largest chunk (the gap shrinks as live tensors grow to dominate the fixed context + pool overhead). The charts use NVML whole-GPU 'used' on a dedicated GPU. Two caveats on that meter: it is a 50 ms poll (a sub-interval spike could be missed), and the frameworks run under different allocator settings (JAX with pre-allocation off; torch with its caching allocator on), so NVML is a neutral meter over somewhat different protocols.

Four measured views vs chunk (per-subject median, 25 subjects). Context floor (pre-fit NVML, before model/data) is ~1 GiB and flat for all four — the frameworks do not differ in the pre-fit baseline (kernel/cuDNN loaded later during the fit falls into the resident/pool remainder, not here). Allocator-live and NVML total scale steeply with chunk for the torch impls but stay ~flat for jamica (its chunked path holds a chunk-independent resident/pool footprint). NVML ÷ allocator shows how much each framework's own counter understates the whole-GPU footprint (~1.2–3.3×): largest for jamica at small chunks (~3.3×, its ~5.4 GiB NVML over a ~1.6 GiB allocator peak — the gap is JAX pool + resident data, not context), shrinking toward ~1.2× as live tensors grow to dominate.

jamica memory is two-level, and it cuts both ways. On its chunked path jamica's median NVML is ~5.4 GiB across chunk sizes (per-subject ~3.4–5.4 GiB below 262K, rising to 5.4–7.4 GiB at 262K for the longest recordings — flat in the median across chunk, a floor, not a single constant). Its full-batch path (chunk_size=None — a different orchestrator key, and jamica's shipped default) uses ~13.4 GiB NVML median (per-subject up to ~21 for the longest recording) for essentially the same GPU speed (~0.020 vs ~0.020 s/iter — no chunk benefit on GPU; the full-batch figure is from the earlier memory run). On CPU, jamica's full-batch key is likewise far heavier than its chunked path (~20 GiB RSS vs a few GiB chunked; earlier fir 1000-iter measurement — the full-batch key was not re-run on Narval). So under these tested conditions a wrapper should pass a chunk. The flip side, in fairness: jamica's ~5.4 GiB chunked floor is higher than the torch impls' small-chunk footprint (~1.8–3.1 GiB NVML) — on a small card the torch impls at a small chunk fit where jamica may not. (The "fits an 8–12 GiB card" reading is an extrapolation from H100 NVML with JAX pre-allocation off; it was not measured on such a card.)

"Flat jamica memory" is not the earlier full-batch measurement bug. Flat memory was the signature of a fixed bug where jamica was accidentally run full-batch at every chunk, so we checked. Two things rule it out here: (1) jamica's fit time varies ~13× with the chunk (775 s→61 s) — only possible if the chunk is actually applied; the true full-batch path is chunk-independent in time too (~61 s at every chunk). (2) The chunked path's memory (~5.4 GiB NVML / ~1.9 GiB allocator) is less than half the full-batch path's (~13.4 / 8.2 GiB) — different numbers, different code path (both in raw/chunk_gpumem_summary.csv). The chunked NVML is flat because of what it's made of: the measured context floor is only ~1 GiB (chunk-independent, and about the same for JAX and torch — see the decomposition above), and the rest of the ~5.4 GiB is JAX's memory pool plus chunk-independent resident arrays (the whitened data and source outputs, sized by n_samples); the framework allocator counter (peak_bytes_in_use ~1.9 GiB) undercounts that resident/pooled footprint the most for JAX, which is why jamica's NVML sits far above its allocator peak. The chunk-scaled E-step block buffer is small next to the resident arrays until 262K, where it begins to add (allocator 1.6→1.9 GiB; per-subject NVML up to ~7.4). So chunk is a real time dial for jamica but not a GPU-memory dial — a genuine property of the chunked path, distinct from the full-batch key. And it is by design, not a leak: the chunked E-step accumulates small per-chunk sufficient statistics (O(n_comp²)) and never materialises the full-width (n_comp, n_samples) per-sample tensors — those appear only on the full-batch path. Of the ~5.4 GiB whole-GPU NVML, only ~1 GiB is the measured pre-fit context floor and ~1.6 GiB is the allocator's live-tensor peak (resident whitened data + accumulators); the remaining ~2.4 GiB is JAX pool / resident bytes the allocator counter does not report / post-init runtime, which we do not separate further — it is chunk-independent (see the decomposition above). Chunking bounds the chunk-scaled working set as intended; it simply cannot go below that context + pool + resident-data floor (which is not a ~3.8 GiB context — the context alone is ~1 GiB).

Convergence vs iterations — the measured iteration ladder

A direct, measured ladder (not a post-hoc estimate): at a fixed chunk (65536) with early-stops disabled, we ran every implementation to 100, 250, 500, 1000, 2000 and 3000 iterations and recorded wall time, final log-likelihood, and peak memory at each — all 25 subjects at every point.   • jamica converges fastest in both iterations and wall time. It is within ~0.001 nats of its own final LL by ~500 iterations (−1.1013 at 500 → −1.1005 at 3000), and because it is ~4–5× cheaper per iteration it gets there in ~14 s — versus ~51–57 s for the others to run the same 500 iterations.
  • pyamica reaches the best (least-negative) reported LL (−1.0995) but uses most of the budget to squeeze the last fraction; amica-python tracks it and plateaus around −1.1006.
  • pAMICA stays ~0.011 nats lower across the whole ladder. Its LL climbs from −1.1293 (100) to −1.1107 (3000) but never reaches the other three's ~−1.100. It is still improving at the end (~0.0016 nats over the last 1000 iters, vs ≤0.0001 for the others), so this is a genuine convergence-quality gap at matched iterations — not an early-stop artifact. We did not run past 3000, so the honest claim is that the gap persists through 3000 and is not closing at any practical budget, not that it can never close.

  • No small-chunk advantage on CPU — but the optimum is implementation-specific, not uniformly large. Small chunks (1K) are best for none of the Python/JAX impls: jamica and amica-python minimize at the largest chunk (262K), while pAMICA and pyamica minimize at a mid chunk (16K) — pyamica is ~10% slower at 262K and ~2× slower at 64K, and pAMICA also bumps at 64K, so the curves are non-monotonic, not a smooth "bigger is better". The earlier shared-cluster result (small/mid chunks win on CPU) did not replicate under whole-node isolation — contention was a likely confound, though the runs also differ in platform and budget, so we don't claim it was the sole cause. Fortran (single-threaded) is roughly flat, marginally best at 1K.
  • CPU AMICA is a heavy method — even at 250 iterations it is ~13–25 min per fit for the Python impls and ~1 h for the single-threaded Fortran; at a full 3000-iteration budget that is hours. A GPU remains far preferable.
  • Memory grows with chunk on CPU (jamica ~2.3→10.4, pyamica ~2.1→9.6, pAMICA ~1.6→6.1 GiB from 1K→262K); the single-threaded Fortran reference is leanest (0.8→3.1 GiB). RSS is iteration-independent, like VRAM on the GPU.
On the CPU numbers. These are the clean re-run: whole-node exclusive (one fit per node) removes the memory-bandwidth contention that blurred the earlier shared-cluster measurement, so the absolute seconds are meaningful. The per-subject bands are tighter than the contended run but not uniformly small (relative IQR ranges from ~8% to ~35–39% across cells), so adjacent-chunk differences of a few percent are not robust — trust the curve shapes and the death of the small-chunk story, not an exact certified optimum. Iteration-matched to 250 (early-stops disabled), all 25 subjects, all five implementations. The four Python/JAX impls were given the whole node (64 threads via OMP/MKL/OpenBLAS); Fortran is single-threaded (OMP_NUM_THREADS=1), so a whole 64-core node is a fair-isolation, not a fair-thread, comparison for it — read it as a reference footprint.
